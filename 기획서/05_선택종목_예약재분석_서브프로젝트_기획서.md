# ThesisGuard 선택 종목 예약 재분석 및 이메일 알림 기능

## 1. 문서 목적

이 문서는 사용자가 원하는 보유 종목만 선택하고 종목별 분석 시간을 설정하면, 시스템이 매일 해당 시각에 최신 정보를 재분석하고 투자 논리의 의미 있는 변화를 이메일로 알리는 기능을 A·B·C 세 역할이 병렬로 개발할 수 있도록 정의한다.

담당자 표기:

- A: Frontend & Product
- B: Backend & Data Infra
- C: AI / Agent Core

## 2. 제품 정의

### 2.1 핵심 사용자 흐름

1. 사용자가 보유 종목 중 자동 분석할 종목을 선택한다.
2. 선택한 종목마다 하루 한 번 실행할 시각을 설정한다.
3. Backend가 설정을 저장하고 다음 실행 시각을 계산한다.
4. 예약 시각이 되면 시스템이 해당 종목의 최신 공시·뉴스·시장·거시 정보를 수집한다.
5. AI Agent가 최신 정보와 기존 투자 논리를 비교한다.
6. Backend가 분석 결과와 Thesis Version을 저장한다.
7. 의미 있는 변화가 있으면 사용자 이메일로 변화 요약과 근거를 발송한다.
8. 변화가 없으면 이메일을 보내지 않고 실행 이력만 저장한다.

### 2.2 MVP 포함 범위

- 보유 종목별 자동 분석 활성화·비활성화
- 종목별 하루 1회 분석 시각 설정
- IANA 타임존 지원, 기본값 `Asia/Seoul`
- 지정 시각 최신 정보 자동 수집 및 재분석
- 이전 분석과 신규 분석 비교
- 의미 있는 투자 논리 변화가 있을 때 이메일 발송
- 마지막 실행 시각, 다음 실행 시각, 실행 결과 표시
- 실패 기록 및 제한적 자동 재시도
- 중복 분석과 중복 이메일 방지

### 2.3 MVP 제외 범위

- 초단위 또는 실시간 모니터링
- 특정 날짜에 한 번만 실행하는 예약
- 요일별로 다른 시각 설정
- 여러 수신 이메일 등록
- 사용자 개인 Gmail 계정으로 직접 발송
- SMS, 카카오톡, 모바일 푸시
- 매수·매도 추천 또는 자동매매

### 2.4 기본 정책

- 자동 분석은 사용자가 활성화한 종목에만 적용한다.
- 예약은 종목별 매일 반복한다.
- 모든 DB 시각은 UTC로 저장하고 사용자 화면에서는 설정 타임존으로 변환한다.
- 설정 시각이 오늘 이미 지났다면 최초 실행은 다음 날로 계산한다.
- 의미 있는 변화가 있을 때만 이메일을 발송한다.
- 변화가 없거나 근거가 부족하면 실행 이력만 저장한다.
- 동일한 예약 실행에는 이메일을 최대 한 번만 발송한다.
- 이메일 수신 주소는 MVP에서 로그인 사용자의 계정 이메일을 사용한다.

## 3. 성공 기준

- 선택하지 않은 종목은 자동 분석되지 않는다.
- 종목마다 서로 다른 실행 시각을 설정할 수 있다.
- 예약 시각에 분석이 자동 실행되고 결과가 기존 데이터 구조에 저장된다.
- 의미 있는 변화가 발견되면 근거를 포함한 이메일이 한 번 발송된다.
- 변화가 없으면 이메일이 발송되지 않는다.
- 서버 재시작이나 일시적 실패가 중복 실행·중복 발송으로 이어지지 않는다.

# 서브 프로젝트 A — Frontend & Product

## A-1. 프로젝트명

선택 종목 자동 분석 설정 UI

## A-2. 목표

사용자가 자동 분석 대상 종목과 실행 시각을 쉽게 설정하고, 현재 예약 상태와 최근 실행 결과를 확인할 수 있는 화면을 구현한다.

## A-3. 사용자 스토리

- 사용자는 보유 종목 중 자동 분석이 필요한 종목만 선택할 수 있다.
- 사용자는 종목마다 원하는 분석 시각을 설정할 수 있다.
- 사용자는 자동 분석을 언제든 중지하거나 다시 활성화할 수 있다.
- 사용자는 마지막 분석 시각과 다음 예정 시각을 확인할 수 있다.
- 사용자는 최근 자동 분석의 성공·실패 여부를 확인할 수 있다.
- 사용자는 이메일이 어느 주소로 발송되는지 확인할 수 있다.

## A-4. 화면 요구사항

### A-4.1 보유 종목 카드

각 종목 카드에 다음 항목을 추가한다.

- 자동 분석 토글
- 매일 실행 시각 입력
- 타임존 표시
- 수신 이메일 표시
- 마지막 실행 시각과 결과
- 다음 실행 예정 시각
- 설정 저장 버튼

표시 예시:

```text
NVDA

자동 분석: ON
분석 시각: 매일 21:00
타임존: Asia/Seoul
수신 이메일: user@gmail.com

마지막 분석: 2026-07-14 21:00 성공
다음 분석: 2026-07-15 21:00
```

### A-4.2 자동 분석 관리 화면

자동 분석이 활성화된 종목을 한 화면에서 관리한다.

- 종목코드
- 회사명
- 실행 시각
- 활성화 여부
- 마지막 실행 결과
- 다음 실행 시각
- 수정 및 해제 버튼

### A-4.3 UI 상태

- 초기 조회 중
- 저장 중
- 저장 성공
- 잘못된 시각 형식
- 투자 논리가 등록되지 않은 종목
- API 요청 실패
- 최근 자동 분석 실패
- 자동 분석 비활성화

## A-5. API 연동

- 반응형 화면 처리

- 실제 Backend API 통합 테스트

## A-7. 완료 조건

- [ ] 선택한 종목만 자동 분석 대상으로 설정할 수 있다.
- [ ] 종목별로 서로 다른 시각을 저장할 수 있다.
- [ ] 새로고침 후에도 설정이 유지된다.
- [ ] 자동 분석을 해제하면 다음 실행 시각이 표시되지 않는다.
- [ ] 소유하지 않은 종목의 예약은 조회·수정할 수 없다.

# 서브 프로젝트 B — Backend & Data Infra

## B-1. 프로젝트명

종목별 예약 실행·분석 저장·이메일 발송 시스템

## B-2. 목표

사용자의 종목별 예약을 저장하고, 지정 시각에 분석 워크플로를 안전하게 실행하며, 결과 저장·실패 재시도·이메일 발송을 담당한다.

## B-3. 데이터 모델

### B-3.1 `analysis_schedules`

| 필드 | 타입 | 설명 |
|---|---|---|
| `id` | UUID PK | 예약 ID |
| `holding_id` | UUID FK, UNIQUE | 대상 보유 종목 |
| `enabled` | BOOLEAN | 예약 활성화 여부 |
| `daily_time` | TIME | 현지 기준 매일 실행 시각 |
| `timezone` | VARCHAR | IANA 타임존 |
| `recipient_email` | VARCHAR | 수신 이메일 |
| `last_run_at` | TIMESTAMPTZ nullable | 마지막 실행 시각 |
| `next_run_at` | TIMESTAMPTZ | 다음 실행 시각 |
| `created_at` | TIMESTAMPTZ | 생성 시각 |
| `updated_at` | TIMESTAMPTZ | 수정 시각 |

제약조건:

- 한 `holding_id`에는 하나의 예약만 존재한다.
- `next_run_at`은 Backend가 계산한다.
- `recipient_email`은 로그인 사용자 이메일로 설정한다.

### B-3.2 `scheduled_analysis_runs`

| 필드 | 타입 | 설명 |
|---|---|---|
| `id` | UUID PK | 실행 ID |
| `schedule_id` | UUID FK | 예약 ID |
| `holding_id` | UUID FK | 대상 보유 종목 |
| `scheduled_for` | TIMESTAMPTZ | 원래 실행 예정 시각 |
| `started_at` | TIMESTAMPTZ nullable | 실제 시작 시각 |
| `completed_at` | TIMESTAMPTZ nullable | 완료 시각 |
| `status` | ENUM | `PENDING/RUNNING/SUCCEEDED/FAILED/SKIPPED` |
| `thesis_version_id` | UUID nullable | 생성된 버전 ID |
| `alert_id` | UUID nullable | 생성된 알림 ID |
| `email_sent` | BOOLEAN | 이메일 발송 여부 |
| `retry_count` | INTEGER | 재시도 횟수 |
| `error_message` | TEXT nullable | 실패 원인 |
| `created_at` | TIMESTAMPTZ | 생성 시각 |

중복 방지 제약조건:

```text
UNIQUE(schedule_id, scheduled_for)
```

## B-4. REST API

```text
GET    /api/analysis-schedules
GET    /api/holdings/{holding_id}/analysis-schedule
PUT    /api/holdings/{holding_id}/analysis-schedule
DELETE /api/holdings/{holding_id}/analysis-schedule
```

검증 규칙:

- 로그인 사용자가 소유한 종목만 설정할 수 있다.
- 투자 논리가 등록된 종목만 자동 분석을 활성화할 수 있다.
- `daily_time`은 `HH:mm` 형식이어야 한다.
- `timezone`은 유효한 IANA 타임존이어야 한다.
- 사용자 이메일이 없으면 예약 활성화를 거부한다.

## B-5. 분석 서비스 분리

현재 수동 분석 API의 실행·저장 로직을 공용 서비스로 분리한다.

```python
async def analyze_holding_service(
    db,
    user,
    holding,
    trigger_type,
) -> HoldingAnalysisResponse:
    ...
```

`trigger_type` 값:

```text
MANUAL
SCHEDULED
```

수동 분석 API와 예약 Worker가 같은 서비스를 호출해야 하며, 분석 결과 저장 방식도 동일해야 한다.

## B-6. 예약 Worker

Worker는 약 1분마다 다음 작업을 수행한다.

1. `enabled=true`이고 `next_run_at <= now`인 예약을 조회한다.
2. 원자적으로 실행 권한을 확보한다.
3. `scheduled_analysis_runs`에 실행 이력을 생성한다.
4. 대상 종목의 분석 서비스를 호출한다.
5. Thesis, Thesis Version, Evidence, Analysis Result, Alert를 저장한다.
6. `alert_decision.should_send`가 참이면 이메일을 발송한다.
7. 실행 결과와 이메일 발송 결과를 기록한다.
8. `next_run_at`을 다음 날로 변경한다.

다중 Worker 환경에서는 DB 잠금 또는 원자적 상태 변경으로 동일 예약의 중복 실행을 방지한다.

## B-7. 실패 및 재시도 정책

- 분석 실패: 최대 2회 재시도
- 재시도 간격: 5분, 15분
- 이메일 실패: 분석 성공 상태는 유지하고 이메일만 재시도
- 서버 재시작: 미완료 예약을 다시 조회
- 예약 시각에서 12시간 이상 지난 작업: `SKIPPED` 처리 후 다음 예약 계산
- 동일 종목 분석이 이미 진행 중이면 중복 실행하지 않는다.

## B-8. 이메일 발송

MVP에서는 서비스용 Gmail 계정 하나를 SMTP 발신 계정으로 사용한다.

```dotenv
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_USERNAME=service@gmail.com
SMTP_PASSWORD=
SMTP_FROM_EMAIL=service@gmail.com
SMTP_USE_TLS=true
EMAIL_DRY_RUN=false
```

이메일 내용:

- 종목명과 종목코드
- 분석 실행 시각
- 이전 상태와 현재 상태
- 신뢰도 점수 변화
- 변화 요약
- 충돌한 핵심 전제
- 신규 위험
- 관찰 포인트
- 주요 근거와 원문 URL
- 투자 권유가 아니라는 안내

이메일 제목 예시:

```text
[MAJOR] NVDA 투자 논리 변화 감지
```

## B-9. 관측성과 보안

로그에 다음 식별자를 포함한다.

- `schedule_id`
- `run_id`
- `holding_id`
- `ticker`
- `scheduled_for`
- 실행 시작·종료 시각
- 재시도 횟수
- Alert severity
- 이메일 발송 결과

API 키, SMTP 비밀번호, 인증 토큰, 이메일 본문 전체는 로그에 기록하지 않는다.

## B-10. 테스트 범위

- 예약 생성·조회·수정·해제
- 소유권 검증
- 다음 실행 시각 계산
- 자정 전후 및 타임존 처리
- 서버 재시작 후 예약 복원
- 동일 예약 중복 실행 방지
- 분석 실패 재시도
- 이메일 실패 재시도
- 변화 없음 시 이메일 미발송
- 변화 있음 시 이메일 1회 발송
- 비활성 종목 미실행

## B-11. 완료 조건

- [ ] 활성화한 종목만 지정 시각에 실행된다.
- [ ] 종목별로 서로 다른 시각을 설정할 수 있다.
- [ ] 동일 예약이 중복 실행되지 않는다.
- [ ] 수동 분석과 예약 분석이 동일한 저장 로직을 사용한다.
- [ ] 변화가 있을 때만 이메일이 발송된다.
- [ ] 실패 원인과 재시도 상태를 DB에서 확인할 수 있다.
- [ ] 테스트 환경에서는 `EMAIL_DRY_RUN`으로 검증할 수 있다.

## B-12. 브랜치

```text
feature/be-analysis-scheduler
```

# 서브 프로젝트 C — AI / Agent Core

## C-1. 프로젝트명

예약 재분석용 투자 논리 변화 판정 고도화

## C-2. 목표

특정 종목의 최신 정보를 기존 투자 논리와 비교하고, 반복 분석에서 발생할 수 있는 불필요한 상태 변화를 줄이면서 이메일 발송이 필요한 의미 있는 변화를 근거와 함께 반환한다.

## C-3. 책임 범위

C가 담당하는 것:

- 최신 정보와 기존 Thesis 비교
- Evidence 분류 및 영향도 판단
- 신뢰도와 Thesis Status 산정
- 충돌한 핵심 전제 식별
- 변화 이유와 관찰 포인트 생성
- Alert Decision 반환

C가 담당하지 않는 것:

- 예약 저장과 실행
- DB 마이그레이션
- 이메일 템플릿과 발송
- 실패 재시도와 중복 실행 방지

## C-4. 변화 판정 기준

### `NONE`

- 새로운 유효 정보가 없다.
- 기존 투자 논리를 재확인하는 정도다.
- 신뢰도 변화가 매우 작다.
- 핵심 전제에 영향이 없다.

반환 정책:

```text
severity=NONE
should_send=false
delivery=NONE
```

### `MINOR`

- 신뢰도에 작은 변화가 있다.
- 낮은 영향도의 신규 위험이 발견된다.
- 일부 관찰 포인트가 추가되지만 핵심 상태는 유지된다.

MVP에서는 반복 알림을 줄이기 위해 즉시 이메일 대상에서 제외할 수 있다. 최종 정책은 B·C 통합 전에 확정한다.

### `MAJOR`

- 투자 논리 상태가 강화 또는 약화 방향으로 변경된다.
- 핵심 전제 중 하나가 강하게 지지되거나 반박된다.
- 신뢰도가 합의된 임계치 이상 변한다.
- 높은 영향도의 신규 위험이 등장한다.

반환 정책:

```text
severity=MAJOR
should_send=true
delivery=IMMEDIATE
```

### `CRITICAL`

- 투자 논리가 `BROKEN`으로 변경된다.
- 핵심 전제가 사실상 무효화된다.
- 회사 공시나 실적자료가 기존 논리를 직접 반박한다.

반환 정책:

```text
severity=CRITICAL
should_send=true
delivery=IMMEDIATE
```

## C-5. B·C 결과 계약

기존 `ThesisAnalysisResult`를 유지한다.

Backend가 사용하는 핵심 필드:

```text
updated_confidence
updated_status
change_reason
conflicting_assumptions
observation_points
evidence
alert_decision.severity
alert_decision.should_send
alert_decision.delivery
alert_decision.reason
```

C는 이메일 본문을 직접 만들지 않는다. B가 결과 계약을 이메일 템플릿으로 변환한다.

## C-6. 구현 항목

- 이전 Thesis와 신규 결과 비교 로직 개선
- 신뢰도 변화 임계치 정의 및 테스트
- 핵심 전제 충돌 감지 강화
- 신규 정보가 없을 때 `UNCHANGED` 처리
- 동일 뉴스·공시 Evidence 중복 제거
- 출처 URL이 없는 근거를 주요 이메일 근거에서 제외
- Alert Decision 정책 테스트 보강
- 기존 `arun_analysis_workflow()` 진입점 유지
- 반복 실행 안정성 평가셋 구축

## C-7. 평가 시나리오

- 새로운 정보가 없는 경우
- 동일 뉴스가 반복 수집된 경우
- 긍정 뉴스 한 건만 추가된 경우
- 실적 가이던스가 소폭 하향된 경우
- 핵심 사업 매출 전망이 크게 하향된 경우
- 기존 핵심 전제가 공시에서 직접 부정된 경우
- 출처가 불분명한 뉴스만 존재하는 경우
- 긍정 근거와 부정 근거가 동시에 존재하는 경우

## C-8. 완료 조건

- [ ] 동일 입력 반복 분석에서 불필요한 상태 변경이 발생하지 않는다.
- [ ] 변화 없음 결과는 `should_send=false`로 반환한다.
- [ ] 변화 있음 결과에는 사람이 이해할 수 있는 변화 이유가 있다.
- [ ] 주요 변화에는 하나 이상의 출처 URL이 연결된다.
- [ ] 기존 수동 분석 테스트가 유지된다.
- [ ] Agent가 DB, 스케줄러 또는 SMTP에 직접 의존하지 않는다.

# 4. 역할 간 책임 경계

## 4.1 A와 B

- A는 시각을 입력하고 예약 상태를 표시한다.
- B가 `next_run_at`을 계산한다.
- A는 브라우저에서 예약 작업을 직접 실행하지 않는다.
- OpenAPI 스키마의 최종 소유자는 B다.

## 4.2 B와 C

- B는 예약, 저장, 재시도, 이메일을 담당한다.
- C는 정보 분석과 변화 판정을 담당한다.
- B는 C의 분석 결과를 임의로 수정하지 않는다.
- C는 사용자 DB나 SMTP를 직접 호출하지 않는다.

## 4.3 A와 C

- A는 C의 Agent를 직접 호출하지 않는다.
- 분석 결과는 B의 REST API를 통해 조회한다.

# 5. 권장 개발 순서

1. B와 C가 `ThesisAnalysisResult`와 Alert Decision 기준을 확정한다.
2. B가 예약 API 요청·응답 스키마를 확정한다.
3. A가 확정된 스키마로 목데이터 UI를 개발한다.
4. B가 DB 마이그레이션과 예약 CRUD API를 구현한다.
5. C가 반복 분석과 변화 판정 로직을 개선한다.
6. B가 수동 분석 로직을 공용 서비스로 분리한다.
7. B가 예약 Worker와 Gmail 발송을 연결한다.
8. A·B API 통합을 진행한다.
9. B·C Agent 통합을 진행한다.
10. 전체 예약 실행 E2E 테스트를 수행한다.

# 6. 전체 인수 테스트

## 시나리오: 선택 종목만 예약 분석

1. 사용자가 NVDA 자동 분석을 매일 21:00 `Asia/Seoul`로 활성화한다.
2. AAPL은 자동 분석을 비활성화한다.
3. 21:00에 NVDA만 분석된다.
4. 새로운 정보가 없으면 이메일이 발송되지 않는다.
5. 다음 날 핵심 전제와 충돌하는 신규 공시가 발견된다.
6. 분석 결과가 새 Thesis Version으로 저장된다.
7. 사용자 이메일로 변화 요약과 근거 링크가 한 번만 발송된다.
8. AAPL에는 분석이나 이메일이 발생하지 않는다.
9. NVDA 예약을 비활성화하면 다음 날부터 실행되지 않는다.

# 7. 협업 체크포인트

- API 및 Pydantic 계약 변경은 A·B·C에게 같은 날 공유한다.
- Alembic 마이그레이션은 B만 작성한다.
- Agent 계약 변경은 C가 제안하고 B가 호환성을 검증한다.
- A는 OpenAPI 계약을 기준으로 타입과 목데이터를 관리한다.
- 각 역할은 자신의 완료 조건과 테스트를 통과한 뒤 통합 브랜치에 병합한다.
